# API 명세서 v10 정정표

**「CBAM_API명세서_v10」 안에서 다른 시트를 가리키는 번호가 이전 버전 기준으로 남아 있다.** 따라가면 엉뚱한 API 가 나온다.

**명세 원본(xlsx)은 이 저장소에 없다.** 그래서 원본을 고치는 대신, **저장소 안에 정정표를 둔다.** 명세를 보고 구현하다 번호가 안 맞으면 여기를 본다.

> ⚠️ **원본이 고쳐지면 이 문서를 지운다.** 정정표가 원본보다 오래 살면 그때부터는 이 문서가 낡은 쪽이 된다.
> 원본 파일을 가진 사람이 아래를 반영하고 이 문서를 삭제하는 PR 을 내면 끝난다.

출처: 이슈 [#12](../../../../issues/12) 에서 v10 시트를 대조한 결과다.

## 1. 내부 참조 번호 7곳

| 적힌 곳 | 적힌 번호 | **v10 기준** | 확인 |
| --- | --- | --- | --- |
| 규약 6항 「화면은 №27로 폴링한다」 | №27 | **№19** 비동기 작업 상태 조회 | ✅ |
| 규약 6항 「작업 실패는 №27이 200 OK」 | №27 | **№19** | ✅ |
| №21 변경사유 「판정 결과는 제출 데이터 상세(№23)에서 조회」 | №23 | **№21** | ✅ |
| 추적표 비고 「초안 조회(№31)가 참조」 | №31 | **№27** 피드백 초안 조회 | ⚠️ |
| 추적표 비고 「발송 이력(№36) status=FAILED 필터」 | №36 | **№31** 발송 이력 조회 | ✅ |
| 추적표 비고 「제출 데이터 상세(№24)에 포함」 | №24 | **№21** | ✅ |
| 규약 4항 「대시보드 요약(№36)·판정 현황(№38)·내재배출량(№17)·발송 결과(№48)」 | — | 어느 체계 번호인지 불명. v10 은 **№24·№12·№31** | ⚠️ |

### 확인 방법 — 무엇을 근거로 ✅ 를 붙였나

**FE 코드가 v10 을 보고 쓰였고, 함수마다 자기 번호와 경로를 문자열로 들고 있다.** 그것과 대조했다.

```
frontend/src/api/index.js
  №19  GET /tasks/{taskId}                    ← 폴링은 №19 다. №27 이 아니다
  №21  GET /submissions/{submissionId}        ← 제출 데이터 상세는 №21 이다
  №23  POST /submissions/{submissionId}/reject   ← №23 은 반려다. 상세가 아니다
  №24  GET /dashboard                         ← №24 는 대시보드다. 상세가 아니다
  №31  GET /suppliers/{supplierId}/feedback-histories  ← 발송 이력은 №31 이다
```

⚠️ **둘은 코드로 확인할 수 없었다.** 지어내지 않고 그대로 남긴다.

- **№27 피드백 초안 조회** — FE 가 그 엔드포인트를 부르지 않는다(초안 **생성** №26 · 확정 №29 · 발송 №30 만 쓴다). 「초안 조회」가 №27 인지 확인할 자료가 코드에 없다
- **규약 4항의 №36·№38·№17·№48** — 어느 버전 체계인지조차 알 수 없다. v10 의 해당 API 는 №24(대시보드)·№12(완제품 상세, 내재배출량 통합)·№31(발송 이력)이다

## 2. 202 를 반환하는 API 개수가 시트마다 다르다

| 어디 | 적힌 수 |
| --- | --- |
| 규약 6항 | **6개** |
| 축소 내역 №31 | **5개** |
| 이슈 #12 의 대조 | **4건** — №14 리마인드 · №26 초안 생성 · №28 재생성 · №30 발송 |
| **FE 코드가 실제로 202/taskId 를 받는 것** | **2건** — №14 리마인드 · №30 발송(최초·재발송) |

**네 숫자가 다 다르다.** FE 가 2건인 것은 명세와 어긋난 것이 아니라 **아직 №26 초안 생성과 №28 재생성을 비동기로 다루지 않기 때문**이다 (목이 `taskId` 없이 바로 초안을 돌려준다).

**원본에서 정할 것** — 202 를 반환하는 API 를 열거하고 그 수를 세 시트에 같게 적는다. 지금은 어느 숫자를 믿어야 하는지 알 수 없다.

## 3. 삭제한 개념이 Enum 설명에 남아 있다

`SubmissionStatus.NOT_SUBMITTED` 의 설명이 이렇다.

> **마감월 개시로 생성됐으나** 자료가 들어오지 않은 상태

**v10 은 「마감월 개시」를 삭제했다.** 그리고 미제출은 제출 데이터 행이 없어 **`id=null` + `target`** 으로 표현한다고 같은 문서가 못박았다. 설명만 이전 버전이다.

FE 는 후자를 따른다 — `Deadlines.unsubmitted()` 가 제출 행이 아니라 **대상 목록**을 돌려준다.

---

## 이 문서를 어떻게 쓰나

- **명세를 보다 번호가 안 맞으면** 위 표를 본다
- **번호를 하나라도 고쳤으면** 여기도 고친다. 두 곳이 다르면 원본이 맞다
- **⚠️ 표시된 둘은 아직 답이 없다.** 지어내 채우지 않는다 — 아는 사람이 채운다
