# ADR-0006: 협력업체 목록 기본 정렬은 업체명순(`companyName`)

- 상태: 채택
- 날짜: 2026-09-03
- 관련 기능: 4번 필터·정렬 (FE) · 3번 리스트 조회
- 근거: 이슈 [#9](../../../../issues/9) 팀 답변 — 「기본정렬 companyName」

## 배경

요구사항 4번의 정렬 기준이 원본에서 **「정렬 : 고민해보기」** 로 비어 있었고, API 명세 v10 도 미결로 남겼다.

**그런데 화면은 이미 「심각도 높은 순」을 기본 정렬로 쓰고 있었다.** API 명세 v10 이 허용하는 sort 키는 `companyName` · `lastSubmittedAt` 둘뿐이다. v3 이 넣었던 `severity` 를 **일부러 뺐고** 이유도 적혀 있다 — 「severity 는 협력업체의 속성이 아니라 제출 데이터에서 파생되는 값이라 정의가 필요하다」.

즉 화면의 기본 정렬이 **서버가 받지 못하는 키**였다. 페이징이 붙는 순간(48곳이 한 화면을 넘어가는 순간) 화면 정렬과 서버 정렬이 어긋난다.

## 검토한 선택지

### A. `companyName` — 업체명순 (고른 것)

- 장점 — **명세가 허용하는 키다.** 서버 정렬과 화면 정렬이 같은 값을 쓴다
- 장점 — 48곳이 **항상 같은 자리에 있다.** 담당자가 찾는 업체를 눈으로 찾을 수 있다
- 장점 — 값이 이미 있다. 아무것도 새로 계산하지 않는다
- 단점 — **급한 것이 위로 오지 않는다.** 미제출 5곳이 목록 중간에 흩어진다

### B. 심각도순

- 장점 — 급한 것이 위로 온다. 검토 대기 목록(29번)의 기본 정렬과 같은 방향이다
- **고르지 않은 이유** — **협력업체의 심각도가 아직 없다.** 심각도는 36번이 규칙 R1~R7 로 제출 데이터에 부여한다(`HIGH`·`MEDIUM`·`LOW`). 협력업체 한 곳에 제출 건이 여러 개일 때 무엇을 그 업체의 심각도로 볼지가 정의되지 않았다
- **고르지 않은 이유** — 그래서 화면이 쓰던 「심각도 높은 순」은 실제로 **판정값 순서**(미제출 → 부적격 → 적격)였다. 심각도라고 이름 붙인 다른 값이었다

### C. `lastSubmittedAt` — 최근 제출순

- 장점 — 명세가 허용하는 다른 한 키다
- **고르지 않은 이유** — **그 필드가 아직 어디에도 없다.** 목 데이터에도, 지금 응답에도 없다. 없는 값으로 정렬하지 않는다

## 결정

**협력업체 목록의 기본 정렬은 `companyName`(업체명순)이다.**

- 화면의 정렬 선택지 첫 번째가 「업체명순」이고, 서버에도 `sort=companyName` 으로 보낸다
- 두 번째 선택지는 **「판정 결과순」**이다 — 미제출 → 부적격 → 검토 대기 → 적격. **심각도라고 부르지 않는다.** 심각도가 아니기 때문이다
- **심각도 정렬은 36번이 심각도를 내려준 뒤에 붙인다.** 협력업체 단위 심각도를 어떻게 정의할지(그 달 제출 건 중 최고 심각도?)는 그때 정한다 — 이 문서는 그것을 정하지 않는다

## 결과

- 쉬워진다 — 4번의 미결 항목이 닫혔다. 요구사항 명세 「아직 정해지지 않은 것」에서 그 줄을 지웠다
- 쉬워진다 — 페이징을 붙일 때 화면과 서버가 같은 키를 쓴다
- **감수한다** — 급한 업체가 위로 오지 않는다. 대신 **판정 결과 필터**와 **대시보드의 할 일 목록**(24번)이 그 역할을 한다
- **비워 둔 것** — 협력업체 단위 심각도의 정의. 36번이 붙기 전에는 만들 수 없다

## 다시 볼 조건

- 36번이 제출 데이터에 심각도를 부여하기 시작하고, **협력업체 단위 심각도의 정의가 정해지면**
- 응답에 `lastSubmittedAt` 이 실제로 들어오면 — 그때 기본값을 다시 볼 수 있다
