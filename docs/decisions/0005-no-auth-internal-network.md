# ADR-0005: 인증·인가를 넣지 않는다 — 사내망을 신뢰 경계로 둔다

- 상태: 채택
- 날짜: 2026-09-03
- 관련 기능: 없음 — 요구사항 1~53번에 로그인·권한이 없다
- 근거: 이슈 [#10](../../../../issues/10) 팀 답변 — 「사내망 전제로 인증을 넣지 않기로 확정」

## 배경

API 명세 v10 규약 2항이 인증·인가를 정의하지 않는다고 **스스로 적어 두고, 착수 전 최우선 선결 과제로 남겼다.**

> [미정 — 착수 전 확정 필요] 요구사항 명세 v3에 로그인·권한 요구사항이 없다.
> 본 명세는 인증·인가 방식을 정의하지 않으며, **X-Operator-Id를 인증으로 간주하지 않는다.**

**지금 정해야 한다.** 확정(31번)·반려(32번)·폐기(48번)가 **행위자를 기록**한다. 누가 눌렀는지를 어디서 얻는지 안 정하면 그 기록이 전부 같은 값이 되고, 나중에 인증을 넣을 때 이미 쌓인 기록을 손댈 수 없다.

## 검토한 선택지

### A. 인증을 넣지 않는다 — 사내망 전제 (고른 것)

- 장점 — **요구사항 53개 어디에도 로그인이 없다.** 명세에 없는 것을 만들지 않는다는 규칙을 그대로 지킨다
- 장점 — 화면 하나, 테이블 하나, 미들웨어 하나를 안 만든다. 3일에 그 셋은 기능 두세 개 값이다
- 단점 — **행위자가 구분되지 않는다.** 확정·반려 기록이 전부 같은 값(`X-Operator-Id: demo`)으로 남는다
- 단점 — 사내망 밖에 그대로 띄우면 아무나 확정·발송을 누를 수 있다

### B. 세션·토큰 로그인을 도입한다

- 장점 — 행위자가 실제로 구분된다. 31번·32번 기록이 감사에 쓸 수 있는 값이 된다
- **고르지 않은 이유** — **요구사항에 없다.** 담당자 계정·권한 모델·로그인 화면·비밀번호 정책이 전부 파생되고, 그중 어느 것도 53개 기능에 없다
- **고르지 않은 이유** — 개발 기간이 3일이다. 핵심 줄(18번 → … → 31번 → 41번)이 아직 끝까지 안 이어졌다. **인증은 그 줄을 한 칸도 앞으로 못 옮긴다**

### C. 담당자를 고르는 간단한 선택 화면만 둔다 (인증 없이 식별만)

- 장점 — 행위자 기록이 살아난다. 로그인 없이 이름만 고른다
- **고르지 않은 이유** — 인증이 아니라 **인증처럼 보이는 것**이 된다. 아무나 남의 이름을 골라 확정할 수 있는데 기록에는 그 이름이 남는다. 없는 것보다 나쁘다

## 결정

**데모 범위에서 인증·인가를 넣지 않는다. 신뢰 경계는 사내망이다.**

- `X-Operator-Id` 는 **인증 수단이 아니라 감사 기록용**이다. 명세 v10 규약 2항 그대로다
- 값은 FE 의 `VITE_OPERATOR_ID` 고정값으로 보낸다 (기본 `demo`). **담당자를 고르는 화면은 만들지 않는다**
- 그래서 **확정·반려 기록의 행위자는 전부 같은 값이다.** 숨기지 않고 이 문서에 적어 둔다

**`/api/v1/internal/**` 의 `X-Internal-Token` 을 누가 관리하는지는 아직 정해지지 않았다.** 이 문서는 그것을 정하지 않는다 — 내부 호출을 실제로 쓰는 기능이 나올 때 정한다.

## 결과

- 쉬워진다 — 로그인 화면·계정 테이블·권한 검사가 없다. 화면은 열면 바로 쓸 수 있다
- **감수한다** — 행위자 기록이 의미를 갖지 않는다. 데모에서 「누가 확정했나」를 보여줄 수 없다
- **감수한다** — **사내망 밖에 배포할 수 없다.** 공개 URL 에 띄우는 순간 이 결정은 깨진다. 배포를 정할 때 이 문서를 다시 본다

## 다시 볼 조건

- 사내망 밖에 노출해야 할 때 — **그 전에 반드시 다시 본다**
- 담당자가 여러 명이고 「누가 확정했는지」가 실제로 필요해질 때
- 협력업체가 직접 접속하는 화면이 생길 때 — 그때는 원청과 협력업체를 구분해야 한다
