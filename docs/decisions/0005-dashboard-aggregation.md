# ADR-0005: 대시보드 집계 모수와 상태값 표기

- 상태: **제안** — 팀 확인 전이다. 아래 「결정」은 38·39·40번을 구현하려면 지금 골라야 했던 값이고, 팀이 다른 값을 고르면 여기부터 고친다.
- 날짜: 2026-09-04
- 관련 기능: 38번 · 39번 · 40번 (CBAM-73)

## 배경

[`REQUIREMENTS.md`](../product/REQUIREMENTS.md)의 「아직 정해지지 않은 것」이 38번을 **「정렬/필터 알잘딱」 — 미결정**으로 두고 있다. 그런데 38·39·40번을 구현하려면 **모수·정렬·집계 범위를 하나씩 골라야만 코드가 나온다.**

이 값들이 PR 본문에만 있으면 merge 뒤에 사라진다. 특히 **상태값을 백엔드는 영어, 화면은 한글로 쓰는 규칙은 53개 기능 전부에 걸리는데**, 지금은 이 PR 본문에만 있어 다른 도메인 담당자가 찾을 수 없다.

## 검토한 선택지

### A. counts/ratio 모수를 target(부품 × 협력업체 조합) 단위로 (고른 것)

- 장점 — API 명세 v10 24행의 응답 예시 숫자(48)가 13행(마감 일정 조회)의 `targets` 예시 숫자와 정확히 일치한다. 두 화면이 같은 모수를 쓴다고 읽힌다
- 장점 — ERD 노트의 「미제출 target = ACTIVE part_supplier 중 대상 월의 유효 submission이 없는 조합」과 같은 정의다
- 단점 — 「업체 몇 곳이 미제출인가」를 바로 읽을 수 없다. 한 업체가 부품 5개를 대면 미제출 5로 센다

### B. 협력업체 단위로

- 장점 — 38번 문장(「업체별 상태와 건수」)에 더 가깝게 읽힌다
- **고르지 않은 이유** — 24행 예시 숫자를 설명하지 못한다. 부품별 마감을 업체 단위로 뭉치면 「5개 중 1개만 낸 업체」를 제출/미제출 어느 쪽으로도 세기 어렵다

## 결정

**모수** — `counts`·`ratio`는 ACTIVE `part_supplier`(target) 단위로 센다. 협력이 끊긴 업체(`supplier.status = INACTIVE`)는 제외한다(요구사항 6번).

**`suppliers[]` 목록** — 모수와 달리 **target 이 없는 업체도 빼지 않는다.** (ACTIVE target 이 있는 업체) ∪ (이번 달 제출이 있는 업체)를 싣는다. 줄이 통째로 빠지는 쪽은 숫자가 틀리는 쪽보다 눈에 안 띈다.

**정렬** — `sort=severity,desc`가 기본이자 현재 유일한 동작이다. 그 업체 제출건의 최고 심각도 내림차순 → 회사명 오름차순. `suppliers[]`에 severity 필드가 없어 명세만으로는 정렬 기준을 알 수 없었다.

**severity 블록** — `status = OPEN`인 경보만 센다. 닫힌 경보까지 세면 「지금 조치할 것」이 아니라 「이번 달에 있었던 일」이 된다.

**상태값 표기** — **백엔드 API 계약은 영어 enum**(`QUALIFIED`·`ACTIVE`·`OPEN`), **화면 표시는 한글**(`적격`·`협력유지중`)이다. `REQUIREMENTS.md` 상태값 표의 한글명은 화면 문구다. 이 규칙은 대시보드만이 아니라 **모든 도메인에 적용된다.**

## 결과

- 24행·13행 두 화면의 숫자가 같은 모수를 쓴다.
- 「업체 몇 곳이 미제출인가」가 필요하면 `suppliers[]`를 세야 한다. `counts`로는 안 된다.
- FE는 영어 enum을 받아 화면에서 한글로 바꾼다. 매핑 표가 FE에 하나 필요하다.
- **이 문서가 「제안」인 동안 위 숫자들은 확정이 아니다.** 팀 확인 전까지 다른 기능이 이 모수에 의존하지 않는 게 낫다.

## 아직 정하지 못한 것

**이 PR 안에서 답을 지어내지 않고 남긴다** (「모르면 채우지 말고, 비우고 사유를 남긴다」).

| | 무엇이 막혀 있나 | 지금 코드 |
| --- | --- | --- |
| **`part`·`part_supplier` 소유권** | 부품(7~10번, #21)과 대시보드가 같은 두 테이블을 다르게 매핑한다. #21은 `part_supplier`를 `@ElementCollection`으로 잡아 **`status` 컬럼이 없다** — 이 대시보드의 모수가 `part_supplier.status = ACTIVE`라서, 부품 화면으로 만든 공급 관계는 집계에 **영원히 안 들어온다** | 두 PR 을 함께 머지하면 여전히 부딪힌다. 기준정보 CRUD 를 가진 #21 이 소유하고 대시보드가 조회 전용으로 재사용하는 쪽이 자연스러워 보인다 |
| **39번 D-7 게이트를 누가 보는가** | 「마감 D-7 이내 미제출 업체를」가 **경보를 만드는 쪽**의 조건인지 **조회하는 쪽**의 필터인지 명세가 말하지 않는다 | 조회는 거르지 않는다. `alert` 행이 있으면 규칙이 걸린 것으로 본다. 조회에서 거르면 지난 달 열린 경보가 화면에서 사라진다 |
| **판정 전 제출(`judgement = null`)을 어디로 세는가** | `counts`는 `qualified`·`unqualified`·`notSubmitted` **3버킷 고정**이고 `JudgementStatus`에는 `PENDING`이 없다. 제출은 했으니 미제출이 아니고, 판정 전이니 적격도 부적격도 아니다 — **계약에 자리가 없다** | 지금은 부적격으로 센다. **이건 모르는 것을 값으로 채운 것이라 틀렸다.** 고치려면 `counts`에 4번째 값을 넣거나 모수에서 빼야 하는데 둘 다 API 계약 변경이다 |
| **R1~R7 → 상태 매핑** | `REQUIREMENTS.md`가 이미 미결정으로 올려 둔 항목이다. 40번 심각도별 건수가 이 위에 올라간다 | 규칙 자체를 코드에서 해석하지 않는다 |

## 다시 볼 조건

- **팀이 모수를 확인해 줄 때** — 확정되면 상태를 「채택」으로 바꾸고 `REQUIREMENTS.md`의 38번 줄을 지운다
- **`part`·`part_supplier` 소유자가 정해질 때** — 대시보드의 `Part`·`PartSupplier` 투영을 지우고 소유 도메인 엔티티를 재사용한다
- **`counts`에 판정 전 자리를 만들 때** — API 명세 v10 24행을 먼저 고쳐야 한다
