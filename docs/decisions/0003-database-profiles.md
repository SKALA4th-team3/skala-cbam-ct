# ADR-0003: PostgreSQL 운영 DB · 프로필별 스키마 검증 정책

- 상태: 채택
- 날짜: 2026-09-03
- 관련 기능: 전체

## 배경

ADR-0002는 H2를 부팅용으로만 두고, 실 DB와 `ddl-auto` 정책은 실제 DB를 정할 때 함께 결정하기로 했다. 협력업체·제출·판정 데이터는 재시작 뒤에도 보존돼야 하므로 운영 DB를 정한다.

## 검토한 선택지

### A. PostgreSQL 운영 DB + H2 개발 DB (고른 것)

- 장점 — 운영 데이터가 인메모리 DB처럼 재시작 때 사라지지 않는다
- 장점 — 개발은 H2로 외부 DB 없이 바로 실행할 수 있다
- 장점 — 운영에서는 Hibernate가 스키마를 바꾸지 않고 불일치만 검증한다
- 단점 — 운영 스키마를 앱 밖에서 먼저 준비해야 한다

### B. H2를 개발·운영에 함께 사용

- 장점 — 별도 DB 접속 정보가 필요 없다
- **고르지 않은 이유** — 인메모리 H2 데이터는 재시작 뒤 남지 않아 제출·판정 이력을 보존할 수 없다

### C. PostgreSQL에서 Hibernate `update` 사용

- 장점 — 엔티티 변경에 따라 개발 중 스키마가 편하게 바뀐다
- **고르지 않은 이유** — 앱 기동이 운영 스키마를 자동 변경하면 변경 이력과 검토 절차를 보장할 수 없다

## 결정

- `dev` 프로필은 H2 인메모리 DB와 `spring.jpa.hibernate.ddl-auto=update`를 사용한다.
- `prod` 프로필은 PostgreSQL을 사용하고 `spring.jpa.hibernate.ddl-auto=validate`로 엔티티와 준비된 스키마의 일치만 확인한다.
- 운영 DB 접속 정보는 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` 환경변수로만 주입한다.
- 운영 스키마 변경은 Flyway 또는 팀이 승인한 버전 관리 SQL로 먼저 적용한다. Hibernate `update`·`create`는 운영에서 사용하지 않는다.

## 결과

- 개발자는 DB를 따로 띄우지 않고 실행할 수 있다.
- 운영 배포는 스키마가 없거나 엔티티와 다르면 기동에 실패한다. 데이터 손실보다 조기 실패를 감수한다.
- 첫 운영 테이블을 만들기 전, 스키마 변경 도구 또는 SQL 적용 절차를 정해야 한다.

## 다시 볼 조건

- 첫 PostgreSQL 스키마를 생성할 때 — Flyway 도입 또는 버전 관리 SQL 절차를 확정한다.
- 운영 DB를 다른 제품으로 교체할 때 — 연결 정보와 스키마 검증 정책을 다시 검토한다.
