# ADR-0004: H2 개발·운영 DB와 프로필별 저장 정책

- 상태: 채택
- 최초 결정: 2026-09-03
- 변경일: 2026-09-04
- 관련 기능: 전체

## 배경

초기에는 개발 환경과 운영 환경의 DB 엔진을 분리하려 했으나, 팀 결정에 따라 개발·운영 환경 모두 H2를 사용하는 방향으로 바뀌었다.

API 명세와 ERD가 정의하는 엔티티, 관계, 필수값과 상태값은 유지한다. 이번 결정은 데이터베이스 엔진과 실행 방식만 변경한다.

## 검토한 선택지

### A. 개발·운영 모두 H2 인메모리 DB

- 장점: 설정이 가장 단순하다.
- 고르지 않은 이유: 운영 데이터를 애플리케이션 재시작 후 보존할 수 없다.

### B. 개발은 H2 인메모리, 운영은 H2 파일 DB (고른 것)

- 장점: 개발자는 별도 DB 없이 즉시 실행할 수 있다.
- 장점: 운영 데이터는 애플리케이션 재시작 후에도 파일에 보존된다.
- 장점: 두 프로필이 같은 H2 엔진을 사용해 SQL 방언 차이가 없다.
- 단점: 단일 파일 기반이므로 다중 인스턴스와 대규모 동시 접속에는 적합하지 않다.

## 결정

- `dev` 프로필은 `jdbc:h2:mem:cbam` 인메모리 DB를 사용한다.
- `prod` 프로필은 기본적으로 `jdbc:h2:file:./data/cbam` 파일 DB를 사용한다.
- 두 프로필 모두 Hibernate `ddl-auto=update`로 ERD에 대응하는 JPA 엔티티 스키마를 관리한다.
- H2 콘솔은 개발 프로필에서만 활성화하고 운영 프로필에서는 비활성화한다.
- 운영 DB 경로를 바꿀 때만 `DB_URL` 환경변수로 H2 JDBC URL을 주입한다.
- 생성되는 `data/`, `*.mv.db`, `*.trace.db` 파일은 Git에 커밋하지 않는다.

## 결과

- 별도 DB 서버, 외부 JDBC 드라이버와 Docker Compose가 필요하지 않다.
- 개발 데이터는 애플리케이션 종료 시 사라진다.
- 운영 데이터는 기본적으로 `backend/data/cbam.mv.db`에 보존된다.
- 스키마는 DB 전용 초기화 SQL이 아니라 JPA 엔티티를 기준으로 생성·갱신된다.

## 다시 볼 조건

- 여러 애플리케이션 인스턴스가 같은 DB에 동시에 접근해야 할 때
- 데이터 규모나 동시 접속량이 H2 파일 DB 범위를 넘어설 때
- 운영 스키마 변경 이력을 별도 마이그레이션 도구로 관리해야 할 때
