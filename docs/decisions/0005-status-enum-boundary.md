# ADR-0005: 상태값은 서버가 영문 enum, 화면이 한글 — 변환은 FE 경계 한 곳에서 한다

- 상태: 채택
- 날짜: 2026-09-03
- 관련 기능: 3번·4번 협력업체 목록 · 29번 검토 대기 목록 · 「상태값」 절 전체
- 근거: 이슈 [#8](../../../../issues/8) 팀 답변

## 배경

요구사항 명세와 API 명세가 **같은 값을 다른 말로** 정의한다.

| | 값 |
| --- | --- |
| 요구사항 명세 「상태값」 | `협력유지중` · `협력끊김` · `검토 대기` · `적격` · `부적격` · `미제출` |
| API 명세 v10 Enum | `ACTIVE` · `INACTIVE` · `REVIEW_PENDING` · `QUALIFIED` · `UNQUALIFIED` · `NOT_SUBMITTED` |

**둘 다 맞다.** 요구사항 명세는 「명세가 쓰는 말을 코드에서도 그대로 쓴다」고 못박았고, API 명세는 영문 enum 으로 응답을 정의한다. 정해지지 않은 것은 **어디서 변환하는가** 하나였다.

**지금 정해야 한다.** FE 목 데이터가 한글을 그대로 들고 있어서, **실서버를 붙이는 순간 화면 필터가 전부 빈 목록이 된다.** 협력사 목록의 거래 상태 필터가 `협력유지중` 으로 비교하는데 서버는 `ACTIVE` 를 준다. 붙이는 날 화면 열 곳을 동시에 고치게 된다.

## 검토한 선택지

### A. BE 는 영문 enum 만 내려주고, FE 가 경계 한 곳에서 바꾼다 (고른 것)

- 장점 — **화면 코드와 요구사항 명세가 한글 그대로 유지된다.** 명세를 읽고 화면 코드를 열면 같은 말이 나온다
- 장점 — 바꾸는 자리가 **두 곳뿐이다.** 매핑표(`api/enums.js`)와 응답이 지나가는 한 지점(`api/client.js` 의 `request()`)
- 장점 — 목(한글)과 실서버(영문)를 **같은 코드로 받는다.** 매핑에 없는 값은 그대로 통과하므로, 목으로 돌리는 동안에도 변환기가 붙어 있다
- 단점 — 매핑표가 하나 늘어난다. enum 이름이 바뀌면 이 파일도 따라 고쳐야 한다

### B. BE 가 표시용 라벨을 응답에 함께 담아 준다 (`{ code, label }`)

- 장점 — FE 에 매핑표가 없다. 라벨이 바뀌어도 FE 를 안 고친다
- **고르지 않은 이유** — **API 명세 v10 의 응답 모양을 바꿔야 한다.** 계약이 이미 enum 단일값으로 서 있고, BE 3명이 그것으로 구현 중이다. 3일에 계약을 흔드는 값이 아니다
- **고르지 않은 이유** — 한글 라벨이 BE 코드 안에 박힌다. 문구를 고치려고 BE 를 배포하게 된다

### C. API 도 한글 상태값을 그대로 쓴다

- 장점 — 변환이 아예 없다. 요구사항 명세와 응답이 같은 말이다
- **고르지 않은 이유** — **API 명세 v10 이 이미 enum 으로 정의됐다.** 이걸 뒤집으면 BE·FE 양쪽이 다시 짠다
- **고르지 않은 이유** — DB 컬럼·인덱스·로그에 한글이 들어간다. 되돌리기 어려운 쪽으로 간다

## 결정

**BE 응답은 API 명세 v10 대로 영문 enum 이다. FE 가 표시 직전에 한글로 바꾼다.**

| 방향 | 어디서 | 무엇을 |
| --- | --- | --- |
| 응답 | `api/client.js` 의 `request()` | 모든 응답이 이 한 곳을 지나간다 — `fromServer()` 로 enum → 한글 |
| 요청 | 각 엔드포인트 함수 | 필터·정렬은 `toServer()` 로 한글 → enum. **서버에는 언제나 enum 을 보낸다** |
| 매핑표 | `api/enums.js` | 이 표 말고 다른 곳에 상태값 문자열을 쓰지 않는다 |

**필터의 표시값은 한글, 서버로 가는 값은 영문 enum** 이다. 화면 코드는 한글만 안다.

**매핑에 없는 값은 지어내지 않고 그대로 통과시킨다.** 요구사항 24번과 같은 규칙이다.

## 결과

- 쉬워진다 — BE 가 붙는 날 화면을 고치지 않는다. `.env` 의 `VITE_REAL_API` 에 엔드포인트를 하나씩 넣으면 된다
- 쉬워진다 — 검증이 가능해졌다. `npm run api:verify` 가 **한글로 걸러도 enum 으로 걸러도 같은 46곳이 나오는지** 센다. 변환을 지우면 0곳이 되며 실패한다
- **감수한다** — 매핑표가 늘어난다. enum 이름이 바뀌면 `enums.js` 를 따라 고친다
- **비워 둔 것** — **접수 4값**(`접수 대기`·`미확인`·`접수 불가`·`분석 실패`)과 **피드백 4값**(`초안`·`수정본`·`발송 대기`·`폐기`)은 API 명세의 enum 이름을 확인하지 못해 **매핑하지 않았다.** 지어내지 않고 비워 뒀다 — 확인되면 같은 모양으로 추가한다

## 실서버 확인 (2026-09-04) — 그리고 축이 하나 더 있었다

`dev` 의 BE 를 띄워 확인했다. **결정이 맞았다.**

```
GET /suppliers?status=ACTIVE      → 200
GET /suppliers?status=협력유지중   → 400     ← 화면 값을 그대로 보내면 막힌다
```

**그런데 상태값만이 아니었다 — `country` 도 같은 문제였다.**

```
GET /suppliers?country=KR         → 200
GET /suppliers?country=대한민국    → 400     ← ISO 3166-1 alpha-2 를 요구한다
```

국가는 상태값이 아니라 이 문서가 다루지 않던 축이다. **같은 경계에서 처리한다** — `enums.js` 에 `COUNTRY`(`KR`·`VN`·`ID`) 를 두고 `country` 를 변환 대상 필드에 넣었다. 목 데이터에 있는 세 나라만 넣었다 — 쓰지 않는 나라를 미리 채워 두지 않는다.

**필드 이름은 이 문서가 다루지 않는다.** `companyName`↔`name` 같은 이름 매핑은 `api/shapes.js` 가 따로 맡는다 — 값과 이름은 다른 축이라 섞지 않았다.

## 다시 볼 조건

- BE 가 `{ code, label }` 로 내려주기로 하면 — 그때는 이 문서를 대체한다
- 접수·피드백 enum 이름이 확인되면 매핑표를 채운다. **결정 자체는 바뀌지 않는다**
