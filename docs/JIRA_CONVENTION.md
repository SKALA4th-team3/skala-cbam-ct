## 이 저장소에서 원문과 다르게 정한 것

**원문이 정하지 않았거나, 이 저장소 사정에 맞춰 좁힌 것은 아래 셋뿐이다.** 그 밖에는 원문 그대로다.

| | **이 저장소** | 왜 |
| --- | --- | --- |
| 이슈 제목 | **요구사항 번호로 시작한다** — `24번 추출값을 표준 단위로 변환` | 요구사항 번호가 저장소의 공용어다. 커밋·PR에 다 있는데 보드에만 없으면 매칭이 안 된다. **브랜치명이 이슈 키뿐이 된 뒤로는 이 제목이 키↔번호를 잇는 유일한 자리다** |

| 「완료」 시점 | **`feature/* → dev` PR이 머지되면** | 원문은 「PR이 머지되면」이라고만 한다. 우리는 `dev`·`main` 두 단계로 병합하는데, `dev → main` 은 마지막 데모 직전 한 번뿐이라 그걸 기다리면 3일 내내 모든 이슈가 「진행 중」에 쌓인다 |

## 1. 이슈 체계

```
Epic (큰 기능 단위)
 └─ Task (실제 작업 단위)
     └─ Subtask (Task를 더 쪼갠 세부 작업, 선택)
```

| 단계 | 이슈 타입 | 언제 쓰나 |
| --- | --- | --- |
| 1단계 | **Epic** | 여러 Task를 묶는 큰 기능 단위. 하나의 도메인/기능 덩어리를 대표 |
| 2단계 | **Task** | Epic 아래에서 실제로 진행하는 작업 단위. **대부분의 이슈가 여기 해당** |
| 3단계 | **Subtask** | Task를 더 잘게 쪼갠 세부 작업. 단계가 여러 개로 나뉠 때만 **선택적으로** |

> 💡 대부분은 **Task로 등록하면 된다.** Epic은 새 기능 영역을 시작할 때만, Subtask는 **Task 하나를 여러 사람이 나눠 할 때만** 쓴다.

### 이 프로젝트에서는

**한 Task = 한 요구사항 번호 = 한 브랜치 = 한 PR.** 이게 기본 단위다.

Epic 구성은 **첫 회의에서 정한다.** 정해지지 않았다면 [`product/REQUIREMENTS.md`](product/REQUIREMENTS.md)의 대분류를 그대로 쓰는 것을 권한다 — 명세와 보드가 같은 모양이면 찾기 쉽다.

```
⚡ Ⅰ. 원청 — 기준정보        (1번 ~ 17번)
⚡ Ⅱ. 시스템 — 접수와 분석    (18번 ~ 27번, 33번 ~ 37번)
⚡ Ⅲ. 원청 — 검토와 확정      (28번 ~ 32번, 38번 ~ 41번)
⚡ Ⅳ. 피드백                 (42번 ~ 53번)
⚡ 프로젝트 설계 및 문서화
⚡ Test
```

## 2. 이슈 작성 규칙

| 항목 | 규칙 |
| --- | --- |
| **제목** | **요구사항 번호로 시작**하고, 무엇을 하는 작업인지 바로 알 수 있게 간결히 — `24번 추출값을 표준 단위로 변환`. **브랜치명에는 번호가 없다** — 키↔번호를 잇는 곳은 이 제목뿐이다 |
| **상위 항목 (Parent)** | Task는 해당 Epic에, Subtask는 해당 Task에 **반드시** 연결 |
| **담당자 (Assignee)** | 실제 작업할 사람이 본인 지정 |
| **컴포넌트/라벨** | **`BE` / `FE` / `ETC`** 중 담당 영역 지정. `ETC` 는 문서·설정처럼 저장소 전체에 걸리는 것 |
| **우선순위 (Priority)** | 다른 작업과의 의존성을 고려해 **반드시** 설정 |
| **설명 (Description)** | 무엇을, 왜 하는지 구체적으로. **명세의 기능 설명 문단을 그대로 붙여 넣는다** — 요약하면 「~인 경우에만」 같은 조건이 사라진다 |
| **연결된 이슈** | 상위/하위 관계 외에 관련 작업이 있으면 추가로 연결 |
| **문의/논의** | 개인 메신저 대신 **이슈 댓글**로 남겨서 기록 유지 |

**우선순위와 담당자는 보드에만 있다.** 명세는 「무엇을 만드는가」만 정한다 — [`product/REQUIREMENTS.md`](product/REQUIREMENTS.md) 참고.

## 3. 상태 관리

```
할 일 → 진행 중 → 완료
```

- 상태는 **순서대로만** 이동한다 (건너뛰지 않음).
- 작업을 시작하면 **진행 중**으로.
- **`feature/* → dev` PR이 머지되면 반드시 완료**로 전환한다.
- **Epic은 하위 Task가 모두 완료됐을 때** 완료로 전환한다.

## 4. Git 연동

**브랜치명 또는 커밋 메시지에 Jira 이슈 키가 포함되어야** GitHub와 자동으로 연결된다.

이 저장소는 **둘 다에 넣는다.** 브랜치는 **Jira 이슈 화면의 「브랜치 만들기」로 만들고, 이름은 이슈 키 하나**다.

```
브랜치   CBAM-12
커밋     [BE] Feat: CBAM-12 24번 추출값을 표준 단위로 변환한다
                     └─ 이 키로 연동된다
```

**Jira에서 만들면 이슈 화면에 브랜치·커밋·PR이 자동으로 붙는다.** 손으로 만들면 키 한 글자만 틀려도 아무것도 붙지 않는다 — [ADR-0003](decisions/0003-branch-name-jira-key.md).

형식은 [`GIT_CONVENTION.md`](GIT_CONVENTION.md)를 본다.

## 5. 막혔을 때

**혼자 30분 넘게 막혀 있지 않는다.** 이슈 댓글로 남긴다 — 개인 메신저로 물으면 기록이 안 남아 같은 질문이 반복된다.

명세의 **미결정 항목**(정렬 기준, 규칙→상태 매핑)에 부딪혔으면 **임의로 정하지 말고** 이슈 댓글로 묻는다. 답이 늦으면 PR 본문의 「명세에 없어서 임의로 정한 것」에 적어 두고 넘어간다.
