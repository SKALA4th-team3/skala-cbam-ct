# Git Convention

> **출처** — 팀 작성 「Git Convention」. 이 문서는 그 규칙을 저장소 안으로 옮긴 것이다.
> 원본과 이 문서가 다르면 **원본이 맞다.** 발견하면 이 문서를 고치고 팀에 알린다.
> 원본의 `- 폐기` 토글 안에 있던 구버전(SKP-35 표, `S14P21D208` 표)은 옮기지 않았다.

Jira 이슈를 어떻게 등록하고 관리하는지는 [`JIRA_CONVENTION.md`](JIRA_CONVENTION.md)를 본다.

## 이 저장소에서 원문과 다르게 정한 것

**원문이 정하지 않았거나, 이 저장소 사정에 맞춰 좁힌 것은 아래 다섯뿐이다.** 그 밖에는 원문 그대로다.

| | 원문 | **이 저장소** | 왜 |
| --- | --- | --- | --- |
| 배포 브랜치 | `master` | **`main`** | GitHub 기본 브랜치가 `main`이다. **이름만 다르고 흐름은 원문 그대로다** |
| 도메인 | `be` · `fe` · `ai` | **`be` · `fe` · `etc`** | AI 호출도 Spring Boot 안에서 일어나 `ai` 를 뺐다. 대신 **어느 쪽도 아닌 것**(문서·`.gitignore`·CI)이 갈 곳이 원문에 없어 `etc` 를 넣었다. 커밋 접두어도 `[BE]`·`[FE]`·`[ETC]` |
| 브랜치 이름 | `{type}/{domain}/{feature}` | **Jira 이슈 키 하나** — `CBAM-43` | 브랜치를 **Jira 이슈 화면에서 바로 딴다.** 손으로 옮겨 적으면 키에 오타가 나고, 오타 난 키는 연동이 붙지 않는다 — [ADR-0003](decisions/0003-branch-name-jira-key.md) |
| PR 제목 | 살아 있는 절엔 **형식이 없다** | **커밋 제목과 같은 형식** | 형식을 안 정하면 사람마다 달라진다. 이 규칙은 원문 **「폐기」 표에만** 있던 것이라 여기 적어 둔다 |
| PR 템플릿 `Issue 번호` | `<!-- closed #이슈번호 -->` | **`Issue: CBAM-`** | `closed #N` 은 GitHub Issue 문법이다. 우리는 Jira를 쓰므로 **아무 동작도 하지 않는다** |

## 🌱 브랜치

### 이름

```
CBAM-43
```

**브랜치는 Jira 이슈 화면의 「브랜치 만들기」로 만든다.** 이름은 **이슈 키 하나**다.

```
CBAM-43
CBAM-34
CBAM-51
```

| | |
| --- | --- |
| 만드는 곳 | **Jira 이슈 → 「브랜치 만들기」.** 터미널에서 손으로 만들지 않는다 |
| 이름 | **이슈 키만.** 대화상자가 채워 주는 나머지는 **앞뒤 모두 지운다** — 뒤에 붙는 이슈 제목(`CBAM-43-...`)도, 앞에 붙는 종류(`feature/CBAM-33`)도 |
| 원본 브랜치 | **`dev`.** 대화상자 기본값이 `main` 이면 바꾼다 |

**`{type}/{domain}/{feature}` 는 더 쓰지 않는다** — [ADR-0003](decisions/0003-branch-name-jira-key.md).

#### 브랜치명이 더 이상 알려 주지 않는 것

이름이 키뿐이라 **type · 도메인 · 요구사항 번호가 브랜치명에서 사라졌다.** 셋 다 **보드와 커밋**에 남아 있다.

| 사라진 것 | 어디서 보나 |
| --- | --- |
| `feat` `fix` … | Jira 이슈 타입 · **커밋 제목의 `Feat:`** |
| `be` `fe` `etc` | Jira **컴포넌트/라벨 `BE`·`FE`·`ETC`** · **커밋 접두어 `[BE]`** |
| `24번` | Jira **이슈 제목이 「24번 …」으로 시작한다** · **커밋 제목의 `24번`** |

**커밋 형식은 그대로다.** 브랜치명이 짧아진 만큼 **커밋 제목이 사실상 유일한 기록**이 된다 — `[BE] Feat: CBAM-12 24번 …` 에서 한 자리도 비우지 않는다.

### 워크플로우

```
  feature/*  (개인 기능 단위 작업)
      │
      ▼
     dev     (통합)
      │
      │  ← dev에서 검증 완료 후에만
      ▼
     main    (실운영 / 데모)
```

- **PR은 `feature/* → dev` 로 낸다.**
- `dev → main` 은 **검증이 끝난 뒤에만.** 검증되지 않은 것을 `main` 에 병합하지 않는다.
- **`main` · `dev` 에 직접 push 하지 않는다.** force push·이력 재작성도 하지 않는다.

### 저장소 설정

| | |
| --- | --- |
| GitHub 기본 브랜치 | **`dev`** — 새 PR 의 병합 대상이 자동으로 `dev` 가 된다. clone 하면 `dev` 가 체크아웃된다 |
| `main` | **검증이 끝난 것만.** 직접 push 하지 않는다 |

#### ⚠️ 브랜치 보호 규칙은 걸려 있지 않다. 걸 수 없다

이 저장소는 **비공개 + 무료 조직 플랜**이라 GitHub 이 브랜치 보호를 제공하지 않는다. 설정 화면에 버튼은 보이지만 실제로는 적용되지 않는다.

```
GET .../branches/main/protection
  403  Upgrade to GitHub Pro or make this repository public
```

**확인했다** — `dev` 에 직접 push 해 봤고 **막히지 않고 그대로 들어갔다.**

그래서 아래 둘은 **강제되지 않는다. 사람이 지키는 것이다.**

- `main` · `dev` 에 직접 push 하지 않는다
- force push · 이력 재작성을 하지 않는다

**막아 주는 장치가 없으니 실수하면 그대로 원격에 들어간다.** `git push` 전에 한 번 본다.

```bash
git branch --show-current
```

거는 방법이 없는 건 아니다 — 저장소를 **public** 으로 바꾸거나 **조직 플랜을 올리면** 된다. 지금은 둘 다 안 하기로 했다. 이 프로젝트는 앞으로 협력업체 담당자 이메일과 메일함 설정을 다루므로 public 전환은 가볍게 결정할 일이 아니다.

**최초 부트스트랩 커밋만 `main` 에 직접 올렸다** — 작업 규칙·명세·컨벤션 문서와 Spring Boot·Vue 프로젝트 생성. 리뷰어가 아직 없는 시점이라 PR 이 형식만 남기 때문이다. **그 뒤로는 예외가 없다.**

### 한 브랜치 = 한 Task = 한 PR

**5명이 병렬로 간다. 범위가 겹치면 그날 하루를 충돌 해결에 쓴다.**

브랜치를 만들기 전에 **보드에서** 다른 사람이 같은 번호를 잡고 있는지 본다. **`git branch -a` 로는 이제 키만 보인다** — 그 키가 몇 번인지는 보드만 안다. 이슈의 **컴포넌트 `BE`/`FE`** 가 곧 소유 범위다 — **남의 영역을 고쳐야 하면 먼저 말한다.**

## 📝 커밋

### 형식

```
[BE] Feat: CBAM-12 24번 추출값을 표준 단위로 변환한다

- kg → ton, 원본 값을 raw_value 로 함께 보존
- 변환 불가 시 값을 비우고 conversion_note 에 사유 기록 (24번)
```

| 자리 | |
| --- | --- |
| `[BE]` `[FE]` `[ETC]` | 담당 영역. `[ETC]` 는 문서·설정·CI 처럼 **저장소 전체에 걸리는 것** |
| `Feat:` | 아래 Type 표 |
| `CBAM-12` | **Jira 이슈 키.** 이게 있어야 Jira ↔ GitHub 연동이 동작한다 |
| `24번` | **요구사항 ID.** 원문 형식의 「요구사항ID」 자리다. `[ETC]` 는 해당 번호가 없으면 비운다 |
| 대제목 | 간결하게 |
| 본문 | **반드시 줄바꿈하여** 항목별로. **왜 / 무엇을 / 어떻게** |

**Jira 키와 요구사항 번호 둘 다 넣는다.** 키는 보드와 잇고, 요구사항 번호는 명세와 잇는다 — 하나만으로는 나중에 무엇을 왜 만들었는지 추적할 수 없다.

### Type

| Type | 사용 시점 |
| --- | --- |
| Init | 프로젝트 초기 세팅 |
| Add | 새로운 파일 추가 |
| Delete | 파일 삭제 |
| Feat | 새로운 기능 추가 / 기능 수정 |
| Fix | 버그 수정 |
| Build | 빌드 관련 설정 수정 |
| Chore | 기타 설정 수정 (.gitignore 등) |
| Docs | 문서 및 주석 수정 |
| Style | 코드 스타일 / 포맷 수정 |
| Refactor | 기능 변경 없는 리팩토링 |
| Test | 테스트 코드 추가/수정 |
| Release | 버전 릴리즈 |
| Rename | 파일/폴더 이름 변경 |
| Readme | README 수정 |
| Comment | 주석 관련 작업 |

## 🔀 Pull Request

### 제목

**커밋 제목과 같은 형식을 쓴다.**

```
[BE] Feat: CBAM-12 24번 추출값을 표준 단위로 변환한다
```

제목만 보고도 **무엇을 했는지 알 수 있게** 쓴다.

### 본문

[`.github/pull_request_template.md`](../.github/pull_request_template.md) 가 자동으로 붙는다. 원문 템플릿의 세 절(**한 줄 요약 · 세부 내용 · Issue 번호**)에 **「구현한 요구사항」과 확인 항목들**을 더한 것이다.

**Jira 이슈 키를 제목 또는 본문에 반드시 넣는다.** 연동 앱이 그것으로 이슈를 찾는다.

템플릿의 **「확인하지 못한 것」과 「명세에 없어서 임의로 정한 것」을 비워 두지 않는다.** 없으면 「없음」이라고 적는다 — 비어 있으면 다음 사람은 「했다」인지 「못 했다」인지 알 수 없다.
