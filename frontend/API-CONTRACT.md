# FE ↔ BE 계약 — 기준 문서는 「CBAM API 명세서 v10」이다

**이 파일은 계약서가 아니다.** 계약은 팀이 만든 **CBAM_API명세서_v10** (엔드포인트 31건)이고,
여기에는 **FE 코드가 그 명세와 어긋나는 자리**만 적는다. 명세가 바뀌면 이 파일이 아니라 코드를 고친다.

이전 버전(FE 가 화면을 만들며 임의로 적어 둔 초안)은 폐기했다.

---

## 코드는 명세를 따른다

| | |
| --- | --- |
| Base | `/api/v1` — `VITE_API_BASE` |
| 목록 응답 | `content` · `page`(0부터) · `size` · `totalElements` · `totalPages` |
| 에러 | `{ timestamp, status, code, message, path, details }` · 사유마다 다른 `code` |
| 부분 수정 | **PATCH** (PUT 안 씀) · 상태 전이는 **POST** |
| 담당자 | `X-Operator-Id` 헤더 — **인증이 아니라 감사 기록용** |

엔드포인트 현황은 `npm run api:status` 로 센다. **21건이 명세와 같은 경로·메서드로 선언돼 있고 전부 목이다.**
목이 정한 대로 동작하는지는 `npm run api:verify` 로 센다 — 상태값 경계(ADR-0005)·기본 정렬(ADR-0007)·확정을 **막는 쪽**(31번)을 확인한다.

---

## 아직 어긋나는 것 — 팀이 정해야 한다

### 1. 발송 이력 조회가 협력업체별만 있다 (API №31) — **답을 기다리는 중**

명세는 `GET /suppliers/{supplierId}/feedback-histories` 뿐인데,
**발송 관리 화면은 전체 목록을 보여준다.** 전체 조회 경로가 없다.

`Feedback.list()` 는 №31 경로를 들고 목 데이터를 전체로 돌려준다 — **실서버에서는 그대로 깨진다.**
셋 중 하나를 정해야 한다 (이슈 [#13](../../../issues/13)) — 화면을 협력업체 상세로 옮기거나, 전체 조회를 명세에 추가하거나, 경로를 바꿔 `supplierId` 를 선택 파라미터로 만든다.

### 2. API 명세 v10 내부 참조 번호 — **답을 기다리는 중**

명세 안에서 다른 시트를 가리키는 번호 7곳이 이전 버전 기준으로 남아 있다. 따라가면 엉뚱한 API 가 나온다.
FE 코드는 v10 의 실제 번호를 따라가고 있다. 이슈 [#12](../../../issues/12).

## 닫힌 것

**정해진 것은 여기 남긴다.** 안 남기면 다음 사람이 「아직 어긋난 것」인 줄 알고 다시 논의한다.

### 상태값 한글 ↔ 영문 enum → [ADR-0005](../docs/decisions/0005-status-enum-boundary.md)

**BE 응답은 영문 enum, 화면은 한글.** 변환은 FE 경계 두 곳에서만 일어난다.

| 방향 | 어디서 |
| --- | --- |
| 응답 enum → 한글 | `api/client.js` 의 `request()` — 모든 응답이 지나가는 한 곳 |
| 요청 한글 → enum | 각 엔드포인트의 `toServer()` — **필터·정렬은 서버에 enum 으로 보낸다** |
| 매핑표 | `api/enums.js` |

접수 4값·피드백 4값은 **명세의 enum 이름을 확인하지 못해 비워 뒀다.** 지어내지 않았다 — 확인되면 `enums.js` 에 추가한다.

`npm run api:verify` 가 이것을 센다 — **한글로 걸러도 enum 으로 걸러도 같은 46곳**이 나오는지 본다. 변환을 지우면 0곳이 되며 실패한다.

### 협력업체 기본 정렬 → [ADR-0007](../docs/decisions/0007-supplier-list-default-sort.md)

**업체명순(`companyName`).** 화면이 기본으로 쓰던 「심각도 높은 순」은 명세가 허용하지 않는 키였고,
실제로도 심각도가 아니라 판정값 순서였다 — 두 번째 선택지를 **「판정 결과순」**으로 이름을 고쳤다.
심각도 정렬은 36번이 심각도(R1~R7 → HIGH·MEDIUM·LOW)를 내려준 뒤에 붙인다.

### 인증·인가 → [ADR-0006](../docs/decisions/0006-no-auth-internal-network.md)

**넣지 않는다. 사내망을 신뢰 경계로 둔다.** `X-Operator-Id` 는 인증이 아니라 감사 기록용이고,
`VITE_OPERATOR_ID` 고정값으로 보낸다. **담당자를 고르는 화면은 만들지 않는다** — 확정·반려 기록의 행위자는 전부 같은 값이다.

### 이상치 임계값 → [ADR-0001](../docs/decisions/0001-outlier-threshold.md)

**±30% 고정, IQR 미채택.** 명세 쪽 「IQR 확정 필요」 표기가 낡은 것이다 (이슈 [#11](../../../issues/11)).

### 검토 화면의 「값 입력」 버튼 — 없앴다

담당자가 누락 값을 직접 채우는 기능은 **요구사항 29~32번에 없고 API 도 없다.**
화면에만 채워지고 서버의 `missingFields` 는 그대로여서 확정이 400 으로 막혔다 — 담당자에게는 「채웠는데 안 되는」 상태로 보였다.
**누락 건은 반려(32번) → 피드백 발송(50번)으로 흘려보낸다.** 이슈 [#14](../../../issues/14).

### 부품 엑셀 일괄 등록 (요구사항 №11) — 보류

우선순위가 낮아 **API 를 만들지 않기로 했다. 화면에는 버튼만 둔다** (이슈 [#15](../../../issues/15)).
버튼을 누르면 「아직 준비 중」이라고 말한다 — 하는 일을 숨기지 않는다.
여유가 생기면 행 단위 검증부터 만든다. **오류가 하나라도 있으면 전체를 등록하지 않는다**(11번)가 그때의 완료 조건이고,
**정상 9행 + 오류 1행을 올려 9행도 안 들어가는지** 확인해야 한다.
